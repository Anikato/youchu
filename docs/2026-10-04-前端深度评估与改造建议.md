# 有处前端深度评估与改造建议

日期：2026-10-04。评估基线：本地当前代码，最近提交 `355bbfa`。

## 1. 结论

推荐保留现有 React、Router、TanStack Query、Go 和 SQLite，围绕「找东西、看位置、快速登记、处理归位」重新组织前端。现有业务模型基本贴合家庭目录需求，主要障碍是前端把数据库管理操作直接摆给用户，缺少面向日常任务的信息层级。

优先解决查找可信度和手机操作，再统一视觉。继续添加主题、图标或装饰动画，不能解决这些问题。

三种可选路线：

| 路线 | 收益与代价 | 判断 |
| --- | --- | --- |
| 只改颜色、间距和卡片 | 代价低；查找、查看与编辑混杂的问题仍在 | 不推荐作为主路线 |
| 按任务逐页改造，复用现有 API | 能逐步上线，每一步都能验证；兼容现有数据 | 推荐 |
| 换框架或重写全站 | 迁移、回归成本高；不能自动改善业务交互 | 当前没有必要 |

## 3. 按影响排序的问题

### P0：手机固定保存栏实际失效【实测 + 代码】

在物品页面，CSS 的保存栏是 `position: fixed`，但实际 top 约 2847px、bottom 约 2913px，位于长页面底部；视口高度只有 844px。正常底部导航位于约 782–844px。

根因链：`AppShell` → `PageEnter` → GSAP 对整个页面容器设置位移 → 动画结束仍保留 `matrix(1, 0, 0, 1, 0, 0)` → 容器内 fixed 元素改为相对该容器定位。矩阵没有视觉位移，也仍然不是 `transform: none`。

涉及：`web/src/motion.tsx` 的 `tweenEnter`、`PageEnter`；`web/src/pages.tsx` 的 `AppShell`；`web/src/styles.module.css` 的 `stickySave`、`batchBar`。

推荐：页面壳不做 transform 动画，只保留必要的淡入；固定操作栏和离开确认层放在稳定的壳层或通过 React 自带 portal 渲染。不要只调 z-index。批量栏和离开确认层有相同的祖先关系，应一并验收，尚未逐项实测。

另一个细节：固定栏用 `3.6rem` 假定导航高度，实测导航高度约 61.8px，假定值约 57.6px。应统一导航高度和操作栏偏移，纳入安全区与文字放大验收。

CSS 原理核对：[MDN transform](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/transform)。非 none 的 transform 会为后代 fixed 元素建立包含块。

### P0：查找结果隐藏借出状态【实测 + 代码】

测试里的水晶头钳已有「借出 / 借给邻居」事项，搜索卡片仍只显示原柜格和盒子。用户会把正式归位位置理解为当前可找到的位置。

API 已有 `return_tasks`，首页卡片却仅显示名称、位置和添加时间。进入物品页后，归位事项又排在整段编辑表单和照片之后。

推荐：结果行显示未完成事项；整件取出时突出「借出/待归位」及临时去向，同时把原位置明确写成「归位位置」。部分配件取出则标「部分待归位」，不要把整件判成借出。一个物品多条事项时显示数量并进入详情查看全部。

涉及：`pages.tsx` 的 `ItemListPage`、`ItemEditForm`、`ReturnTaskFields`；现有 `api.ts` 的 `Item.return_tasks`。

### P1：首页几乎不给物品留首屏空间【实测】

390×844 下，第一条物品 top 约 774px，底部导航 top 约 782px。首屏基本只看到控制项。桌面 1280×900 下同样先显示大片控制区域，物品接近页面下部。

原因：标题说明、独立「选择」行、搜索与新增、待定位、整行排序、整行每页、折叠筛选逐项垂直堆叠。调整圆角和间距只能缓解，必须减少首屏控件。

推荐：首页仅保留紧凑标题、搜索、状态筛选和结果；「选择」放在结果工具栏，「每页」放列表底部，「排序」放工具菜单。「新增」保留清晰入口，不与搜索按钮争主操作。

验收目标：390×844 默认首页至少完整看见三条紧凑结果；搜索后也能直接看到命中项。

### P1：点物品得到的是编辑器【实测 + 代码】

`/items/:id` 直接挂 `ItemEditPage`。一件带规格的普通记录打开后有 15 个 input/textarea/select（包含照片文件控件），照片标题约在 1850px。只是想确认东西在哪，也要经过名称输入、放置备注、新建分类、型号规格等控件。

推荐：现有地址默认变成阅读详情；显式「编辑」进入编辑模式。阅读首屏依次显示名称/型号、当前事项、所有存放位置和分放说明、照片；分类和其他资料放后面。保存后回到阅读模式。继续支持原有多位置、多分类及版本冲突。

位置路径应能直接点进对应位置；多位置不能只保留第一条。照片不是必填，没有照片时仍以名称、型号和位置识别。

### P1：位置导航不能直接找到盒子，父位置还会表现为空【实测 + 代码】

位置首页只请求根节点，没有位置搜索。厨房 → 柜格 → 盒子必须逐页进入。测试里厨房下已有大量盒内物品，厨房页却写「这个位置里还没有物品」。

这是直接归属与子树归属混淆。`LocationScreen` 用 `location=id` 查直接物品；后端已有 `in_location=id` 的含下级过滤，不需要新建一套数据模型。

推荐：位置页增加全屋名称/编号搜索，支持展开树浏览；搜索结果显示完整路径，精确编号匹配优先。进入位置默认查看含下级物品，提供「仅直接存放」切换。子位置继续独立展示。空态按当前范围描述。

编号在盒子标题和结果中要醒目，但不会从 `K/B/D/L` 推导业务含义。沿用现有编号和类型规则。

树状浏览可以用已存在的 `fetchAllLocations(flat=1)`，按 parent_id 构建关系、按需展开。不能直接假设扁平接口的 id 顺序等于树顺序。数据特别大时再调整服务端搜索，不提前引入虚拟列表库。

### P1：批量失败反馈可能随退出选择模式消失【代码】

`useItemListBatch.move` 完成后调用 `selection.clear()`，失败信息保存在 `batch.error`；相关页面仅在 selecting 时渲染 BatchBar。归位批量完成、回收站批量恢复及部分撤销失败存在类似反馈依赖。

推荐：成功、部分成功、失败摘要独立于选择模式持续显示；失败行保留选择并可重试。列表仍按现有接口逐条操作。版本冲突必须提示哪一条失败，不能静默覆盖。

批量「放入位置」实际上替换全部原位置和放置说明，当前确认文案有说明，但动作名称容易被理解成追加。改成「更换全部存放位置」；若将来增加「追加位置」，作为独立动作，不混用语义。

### P1：录入被可选操作拖长，照片失败后的恢复成本高【代码】

新建默认展开分类选择和「新建分类」输入；每个已选位置立刻展开至少六行高的放置备注；照片入口位于这些控件之后。只有名称必填，但视觉上仍是完整资料录入。

推荐：主流程是名称、位置、照片；分类以紧凑选择入口呈现，创建分类收进「没有合适分类？新建」。备注、型号等渐进展开。保留按名称即可保存、连续登记及上次位置偏好，用可见提示说明「沿用上次位置/分类」，提供一键清空。

新增照片采用先创建物品再逐张上传。普通上传失败后仅提示「有照片没传上」，随后清空 pendingPhotos；不能直接重试失败文件。认证失败还有物品已创建、页面尚未完成收尾的中间状态。

推荐：保存结果分清「物品已保存」和「照片未上传」；保留失败文件及目标物品 id，重试只上传到已创建物品。成功文件不重复上传，照片失败不重新创建物品。未实测弱网和会话过期，需专项验收。

### P2：分类承担了过多管理职责【代码】

分类选择依靠完整路径原生 select 后再点「添加」，目录越深越难选。分类页面同时展示下级、物品、管理表单。分类物品行缺少首页已有的位置信息，跨页面信息不一致。

推荐：手机仍保留分类浏览入口，覆盖「不记得名字」的场景；分类首页以可展开树和搜索为主，管理收进编辑入口。选择分类用可搜索、多选的轻量面板，点选立即加入；常用分类来自当前浏览器近期选择，不增加后台统计系统。

### P2：搜索能力与用户心智存在落差【代码】

物品搜索目前是名称、别名、型号、备注的整段 LIKE；不包含规格，不查位置编号和分类名，也没有相关性排序。输入 `B101` 不会自动打开该盒子。

推荐：首页同一个输入分别展示「物品」和「位置」结果，位置编号可以直接打开位置，不声称支持自然语言。物品请求沿用现有 API；位置使用已加载树检索。首次完成基础改造后，再按真实使用情况决定是否扩展规格、多关键词及服务端相关性排序。

输入后短暂防抖查询，保留 Enter/查找按钮。输入内容、结果与 URL 要同步；筛选摘要做成可移除的标签。使用旧结果占位时要明确「更新中」，不能把旧位置冒充新结果。

### P2：状态、无障碍和缓存需要统一【代码 / 待验证】

- `RequireAuth` 未区分 me 查询失败和未登录，网络/服务错误也会导航去登录；应显示可重试错误。
- 新建位置选择器 Enter 默认加入第一条，缺少上下键高亮选择和完整 combobox 语义；不要让误选成为正常流程。
- 多选复选框都叫「选择」，应带物品/位置名称；离开对话框需焦点进入、循环和恢复。
- 归位操作后应刷新对应物品状态；分类、位置计数变动后需要刷新相关详情查询，不能只刷新列表查询。当前存在独立的 `item`、`items`、`location`、`locations`、`category`、`categories` 查询键，逐动作列出失效关系即可，不引入新的缓存框架。
- 回到搜索页需要保留筛选、页码和合理滚动位置；当前行为尚未做完整往返实测。

## 4. 推荐的页面结构

手机保留四个入口：找东西、位置、分类、待归位。账号继续作为低频设置入口；回收站可在账号/更多中访问。不给手机首页增加统计仪表盘。

| 页面 | 首要任务 | 默认呈现 | 次要操作 |
| --- | --- | --- | --- |
| 找东西 | 确认有没有、在哪里 | 搜索、状态标签、物品结果；有输入时展示位置命中 | 新增、排序、选择、复杂筛选 |
| 物品详情 | 辨认并找到物品 | 状态、所有位置、照片、资料 | 编辑、换位置、登记借出/带走、回收站 |
| 位置 | 找编号、看柜子/盒子内容 | 搜索/展开树；位置内容默认含下级 | 新建、编辑、移动盒子、克隆空盒 |
| 分类 | 不记得名字时浏览 | 分类树与对应结果，结果显示位置 | 编辑分类、新增子分类 |
| 新增 | 低成本登记 | 名称、位置、照片；可选分类与说明 | 保存、保存并继续 |
| 待归位 | 看临时去向并处理 | 物品、部件、去向、归位位置 | 完成归位、编辑资料、移除事项 |

原来「克隆」容易让人以为连物品一起复制，建议写「新建同款空盒」，保留现有自动编号逻辑。移动盒子继续只改盒子的 parent_id，物品不逐件重写。

视觉方向：家庭目录，清晰、安静、方便核对。沿用苔绿及现有深浅模式，中文系统字体；物品名称第一层、编号/位置第二层、型号/数量第三层。添加时间降为辅助信息。紧凑列表作为默认，桌面可提供照片卡片切换；无照片时用小图标，避免每条巨大「物」字重复占空间。

桌面将搜索和工具栏横向组织，必要时左侧显示位置/分类筛选，右侧显示结果。不要把手机的整列管理控件原样拉到 960px 宽。

## 5. 实施顺序与边界

### 第一批：先恢复可靠操作与查找

1. 移除页面壳 transform 对固定栏/对话框的影响，统一底部导航尺寸。
2. 压缩首页控制区，首屏显示物品；结果展示待归位与临时去向。
3. 批量结果独立显示，保留失败项；纠正更换位置文案。
4. 区分登录失效与网络失败，保留可重试路径。

本批可先作为小范围修复，API 和数据库结构保持现状。

### 第二批：改造核心阅读与定位流程

1. 物品详情默认只读，编辑显式进入，支持位置路径跳转。
2. 全屋位置搜索和展开树；位置内容提供含下级/直接存放切换。
3. 跨列表统一物品行：名称、型号、位置、状态及可选缩略图。
4. 补充查询失效和列表返回状态，验证移动盒子后的完整路径。

### 第三批：降低登记负担

1. 精简新建表单，位置和分类使用可搜索选择面板。
2. 「保存」与「保存并继续」行为明确；继续模式保留位置/分类。
3. 单独处理照片上传状态，失败文件可重试，避免重复物品。
4. 在位置页面提供完整新增入口并预设当前位置，保留仅名称快速录入。

### 第四批：整理维护成本与性能

`pages.tsx` 当前 4877 行，样式 672 行，且有前后多段覆盖。随页面改造拆出对应页面及共享物品行、选择器、固定栏和反馈组件；不先做一次全仓大重构，不为单次使用的表单字段设计通用框架。

构建的主 JS 543.11kB、gzip 164.98kB，Vite 提示大于 500kB。说明存在分包机会，不能据此认定生产慢。账号/图标管理、照片编辑等低频代码可在核心流程稳定后按路由加载。未做真实设备测速，不提前增加缓存层或虚拟化依赖。

不增加 npm 依赖、环境变量，不改现有编号、人工/AI 分类规则、OCC 版本校验、多位置、回收站规则。列表已有分页，继续保留；新增树浏览与搜索不以删除分页为代价。

| 操作失败/断网 | 错误可见且有重试，不把网络故障当作退出登录 |
